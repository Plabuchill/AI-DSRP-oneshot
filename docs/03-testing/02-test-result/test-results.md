## TC-02 — ยืนยัน/ไม่ยืนยัน รง.506 จากหน้ารายละเอียด

**ทดสอบอะไร**: การกระทำเดียวกับ TC-01 แต่ทำจากปุ่มในหน้ารายละเอียด (`506-request-detail.html`) โดยตรง — ต้องได้ผลเหมือนกันทุกประการ (status เปลี่ยน + บันทึกผู้พิจารณา)

**ผล**: ❌ **ไม่ผ่าน** — status เปลี่ยนถูกต้อง (real-time, ปุ่มหายหลังตัดสินใจ) **แต่ไม่บันทึกผู้พิจารณาเลย**

**ติดตรงไหน**:
- รอบแรก (ก่อนแก้โค้ด, 21:04): `approverId`/`approverName` **ไม่ถูกเขียนเลย** (field หายไปจากเอกสาร) — สาเหตุ: โค้ดเดิมของ `506-request-detail.js` เขียนเฉพาะ field `status` โดยตั้งใจ (มี comment "จงใจไม่แตะ approverId/approverName")
- แก้โค้ดแล้ว + deploy (ดู TC-03) + ทดสอบซ้ำ (21:07): `approverId`/`approverName` เปลี่ยนจาก "ไม่มี field" เป็น **`null` ทั้งคู่** — ดีขึ้นระดับหนึ่ง (โค้ดพยายามเขียนแล้วจริง) แต่ค่ายังผิดอยู่ — สาเหตุตรวจสอบแล้วไม่ใช่โค้ดผิด field name (verified `profile.id`/`profile.name` ตรงกับที่ `current-user.js` คืนค่าจริง, ตรวจบัญชี `CUCU1` ใน Firestore ก็มี name/email ครบ, เรียก `getCurrentUserProfile()` สดในหน้าเดียวกันก็คืนค่าถูก) — สรุปเป็น **สมมติฐาน race condition**: ตัวแปร `profile` ที่ปิดอยู่ใน closure ของฟังก์ชัน `decide()` น่าจะถูก resolve ตอนที่ auth state ยังไม่พร้อมจริง (ดูหลักฐานเพิ่มเติมใน TC-06 ที่ชี้ไปทางเดียวกัน) — **ยังไม่ได้แก้ไข ต้องมีคนไปดูโค้ดต่อ**

**Test data**: `506Requests/V8TyCZdGkgxlmLETkqtB` (รอบก่อน deploy), `506Requests/nzbDNagVtjjHvBrZQnwH` (รอบหลัง deploy) — ยังไม่ลบ

## TC-04 — Security: ไม่ล็อกอินแล้วเปิดหน้ารายการ

**ทดสอบอะไร**: เปิด `case-analysis.html` โดยไม่ล็อกอิน (แท็บใหม่ ไม่แตะ session ที่ login อยู่) ต้องอ่านข้อมูลไม่ได้เลย — เกณฑ์ผ่าน = เข้าไม่ได้

**ผล**: ✅ **ผ่าน** — ยืนยัน 2 ชั้น:
1. ฝั่ง UI: เด้งไปหน้า login ทันที, ตรวจ network requests แล้วไม่มีการเรียก Firestore แม้แต่ครั้งเดียวก่อน redirect (ไม่มีข้อมูลรั่ว)
2. ฝั่ง Database: ยิง Firestore REST API ตรงๆ แบบไม่มี auth token (`GET /v1/projects/ai-dsrp/databases/(default)/documents/506Requests`) → ได้ `403 Forbidden` — Security Rules บล็อกจริง ไม่ได้พึ่งแค่การซ่อนหน้า UI

## TC-05 — Security: บัญชีที่สองเปิดข้อมูลบัญชีแรก

**ทดสอบอะไร**: ล็อกอินด้วยบัญชีที่สอง แล้วพยายามเปิด/ดูข้อมูลที่บัญชีแรกสร้างไว้ — เกณฑ์ผ่าน = เข้าไม่ได้

**ผล**: ⏸ **ยังไม่ได้รัน** — บล็อกอยู่ที่ขั้นตอนเตรียมการ ยังขาด:
1. ต้องมีคนล็อกอินด้วยบัญชีที่สองเอง (กรอกรหัสผ่านให้ tester ไม่ได้ตามกฎ)
2. ยังไม่ได้ยืนยันว่า "ข้อมูลของบัญชีแรก" หมายถึงข้อมูลอะไรในระบบนี้จริงๆ — **หมายเหตุสำคัญ**: ตาม `ACL.md` ปัจจุบัน รง.506 ถูกออกแบบให้ทุก role (SRRT/Manager/Director) เห็นรายการ/รายละเอียดของกันและกันได้หมดโดยตั้งใจ (ไม่มีแนวคิด "ข้อมูลส่วนตัวต่อบัญชี" แบบระบบขอลา) ถ้าทดสอบกับ รง.506 ตรงๆ ผลที่คาดคือ "เปิดได้" ซึ่งจะไม่ใช่บั๊ก แต่เป็นไปตาม design — ต้องยืนยัน scope ให้ชัดก่อนรัน

## TC-06 — (พบระหว่างการทดสอบซ้ำ) Manager ที่ login อยู่เข้า `new-506-request.html` ไม่ได้

**ทดสอบอะไร**: ไม่ได้ตั้งใจทดสอบแต่แรก — เจอตอนพยายามสร้างข้อมูลทดสอบซ้ำสำหรับรัน TC-01/TC-02 อีกรอบ

**ขั้นตอน**: login ด้วย `CUCU1` (role manager, ไม่อยู่ในรายชื่อ role ที่ถูกบล็อกหน้านี้ตาม `auth-guard.js`) → เปิด `case-analysis.html` สำเร็จ → เปิด `new-506-request.html` ต่อทันที

**ผล**: ❌ **ไม่ผ่าน — เด้งกลับหน้า login ทั้งที่ login อยู่จริง** — ทำซ้ำ 2 ครั้งติดกัน (สลับกับเปิด `case-analysis.html` คั่นกลางซึ่งสำเร็จทั้ง 2 ครั้ง) ได้ผลเหมือนเดิมทั้ง 2 รอบ คือ `case-analysis.html` เข้าได้เสมอ แต่ `new-506-request.html` เด้ง login เสมอ ในเซสชันเดียวกัน

**ติดตรงไหน**: อ่านโค้ด `auth-guard.js` แล้ว — role `manager` ไม่ได้อยู่ใน `BLOCKED_ROLES_BY_PAGE["new-506-request.html"]` (บล็อกแค่ `director`) จึงไม่ใช่การบล็อกตาม role ที่ตั้งใจ พฤติกรรมที่เห็นตรงกับกรณี `onAuthStateChanged` (บรรทัด 27 ของ `auth-guard.js`)ยิง callback แรกด้วย `user = null` ก่อนที่ Firebase Auth จะโหลด session ที่ persist ไว้เสร็จ (race condition ตอน initialize) แล้วโค้ดเด้ง `login.html` ทันทีโดยไม่รอเช็คซ้ำ — **สอดคล้องกับสมมติฐาน root cause ของ TC-02** (ตัวแปร profile/auth ที่ resolve เร็วเกินไปก่อน auth state พร้อมจริง) ชี้ว่าอาจเป็นปัญหาเชิงระบบที่กระทบหลายหน้า ไม่ใช่บั๊กแยกกัน 2 จุด

**ยังไม่ได้ทดสอบเพิ่ม**: ว่าเกิดกับหน้าอื่นนอกจาก `new-506-request.html` ด้วยหรือไม่ (มีเวลาจำกัดในรอบนี้)
