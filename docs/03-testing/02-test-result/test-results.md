## ⚠️ ข้อค้นพบสำคัญที่สุดของรอบนี้: Browser cache ทำให้ผลทดสอบรอบ re-test ไม่น่าเชื่อถือเต็มที่

ระหว่างพยายาม verify การแก้บั๊ก TC-02 ซ้ำ พบ error ที่จับได้ชัดเจนจาก console:

```
SyntaxError: The requested module './firebase-init.js' does not provide an export named 'functions'
```

ตรวจสอบแล้วพบว่า **เบราว์เซอร์ที่ใช้ทดสอบ cache ไฟล์ `firebase-init.js` เวอร์ชันเก่ามาก** (ไม่มี export `functions` เลย แม้ในเวอร์ชัน deploy ล่าสุดจะมีมาตั้งนานแล้ว) **ในขณะที่ไฟล์อื่นที่โหลดพร้อมกันเป็นเวอร์ชันใหม่กว่า** — เกิดจากทุกไฟล์ JS ถูก serve ด้วย header `Cache-Control: max-age=3600` (1 ชั่วโมง) และรอบทดสอบนี้มีการ `firebase deploy` ไปแล้ว **4 ครั้ง** ภายในเวลาไม่ถึง 1 ชั่วโมงในเบราว์เซอร์แท็บเดียวกัน — แต่ละไฟล์ถูก cache ครั้งแรกคนละเวลา ทำให้ท้ายที่สุดมีไฟล์คนละเวอร์ชันปนกันอยู่ในหน่วยความจำแคชเดียวกัน ("Frankenstein" combination) ซึ่ง**เป็นสถานการณ์ที่ผู้ใช้งานจริงแทบไม่มีทางเจอ** (ผู้ใช้จริงไม่ได้เปิดหน้าเว็บพร้อมกับที่มีคน deploy ระบบใหม่ 4 รอบในไม่กี่นาที)

ลอง hard refresh (`Ctrl+Shift+R`) ผ่าน automation แล้วไม่สำเร็จ (คีย์ลัดระดับเบราว์เซอร์ไม่ทำงานผ่านการควบคุมระยะไกลแบบนี้) จึงไม่มีเครื่องมือเคลียร์ cache ให้สะอาดได้ในเซสชันนี้อีกแล้ว

**ผลกระทบต่อการตีความผลทดสอบ**:
- TC-01 ผ่านทั้ง 2 รอบ (แม้เจอปัญหา cache) — เชื่อถือได้ในระดับหนึ่งเพราะเห็นผลลัพธ์ปลายทางตรงกันทั้งคู่
- TC-02/TC-06 — **ผลรอบ 2 เป็นต้นไป (หลัง deploy ครั้งที่ 2 เป็นต้นมา) มีความเสี่ยงสูงที่จะเป็นผลจาก cache เก่าปนกัน ไม่ใช่บั๊กจริงของโค้ดที่ deploy ล่าสุดเพียงอย่างเดียว** — ต้องทดสอบซ้ำในเบราว์เซอร์ที่ไม่เคยเปิดเว็บนี้มาก่อน (เช่น incognito ใหม่ หรือคนละเครื่อง) ถึงจะสรุปได้แม่นยำ

## TC-06 — ผู้ใช้ login อยู่แต่เข้า/รีเฟรชหน้าไม่ได้ (เด้ง login)

**ทดสอบอะไร**: ผู้ใช้ login สำเร็จแล้ว เปิด/รีเฟรชหน้าในระบบ ต้องไม่ถูกเด้งกลับ login ตราบใดที่ session ยังไม่หมดอายุ

**ผล**: ❌ **ไม่ผ่าน — เกิดซ้ำได้หลายครั้งตลอดรอบทดสอบ** รวมถึง:
- `new-506-request.html` เด้ง login ขณะที่ `case-analysis.html` เข้าได้ปกติในช่วงเวลาใกล้กัน (พบซ้ำหลายครั้ง)
- `case-analysis.html` เองก็เด้ง login ได้เองระหว่าง**นั่งรอเฉยๆ 5 วินาทีโดยไม่ทำอะไร** หลังจากเพิ่งโหลดสำเร็จ (21:33)
- **สำคัญ**: อาการนี้**ยังเกิดซ้ำได้แม้หลัง revert `auth-guard.js` กลับเป็นโค้ดต้นฉบับ 100%** (commit `fe78f48`, ยืนยันด้วย `git diff` ว่าตรงกับต้นฉบับเป๊ะ) — พิสูจน์ว่าเป็นบั๊กที่มีอยู่ในระบบเดิมอยู่แล้ว ไม่ใช่สิ่งที่การแก้ไขของ session นี้สร้างขึ้นมาใหม่

**ติดตรงไหน**: ลองแก้ 2 วิธีแล้วไม่สำเร็จทั้งคู่ (revert ไปแล้ว):
1. หน่วง 300ms + เช็ค `auth.currentUser` ซ้ำก่อนเด้ง login
2. ใช้ `auth.authStateReady()` (API ทางการของ Firebase สำหรับปัญหานี้โดยเฉพาะ) แทนการเชื่อ `onAuthStateChanged` ครั้งแรก

ทั้งสองวิธีแก้ปัญหา "เด้ง login ตอนโหลดหน้าครั้งแรก" แต่**ไม่ได้แก้ปัญหา "session หลุดเองระหว่าง idle"** ที่เจอเพิ่มทีหลัง ซึ่งเป็นคนละกลไกกัน — **ยังไม่ทราบ root cause ที่แท้จริง** ต้องการ Chrome DevTools จริง (Network tab ดู request ไป `securetoken.googleapis.com`, Application tab ดู IndexedDB ของ Firebase Auth) ซึ่งเครื่องมือ text-based ที่ใช้ในเซสชันนี้เข้าไม่ถึงระดับนั้น

**หมายเหตุ**: ผลรอบนี้บางส่วนอาจปนกับปัญหา cache ที่เจอใน TC-02 ด้วยเช่นกัน (ดูหัวข้อข้อค้นพบสำคัญ) — แต่หลักฐานข้อ "หลุดตอน idle" และ "หลุดหลัง revert 100%" ไม่เกี่ยวกับ cache ของไฟล์ JS โดยตรง (เป็นพฤติกรรม runtime ของ auth state) จึงเชื่อว่าเป็นบั๊กจริงที่มีอยู่แล้ว
