# User Journey — วางแผนควบคุมโรคและขออนุมัติเบิกน้ำมัน/น้ำยาเคมีผ่าน Control Plan

อ้างอิงจาก [[../../01-requirements/01-spec/FEATURE-LIST|FEATURE-LIST.md]] หมวด `FEAT-CONTROL` และสอดคล้องกับ Sequence Flow ที่มีอยู่แล้วใน [[../02-technical/DETAILED-DESIGN|DETAILED-DESIGN.md]] Flow 8 (Control Plan Approval Flow), Flow 9 (Spray Workplan Assignment) และ Flow 10 (Location Management) — โมดูลนี้**ยังไม่มี Test Spec** ใน [[../../03-testing/01-test-plan/v1/ACCEPTANCE-CRITERIA|ACCEPTANCE-CRITERIA.md]] เลย (มีแค่ FR-DASH-01 ถึง 06 สำหรับ Outbreak Dashboard) ดูหัวข้อ Traceability ท้ายเอกสาร

> **สถานะโค้ดจริง ณ วันที่เขียน (2026-09-22)**: โมดูลนี้**ทั้งหมดยังเป็น mock ล้วน** ฝังอยู่ใน `control-plan.js` (พื้นที่/ตำแหน่งควบคุมโรค, สถานะพ่นแล้ว, คำขออนุมัติ ทั้งหมดเป็น state ในหน่วยความจำของหน้าเว็บเท่านั้น ไม่มีส่วนไหนต่อ Firestore/Cloud Function จริงเลย — ต่างจาก Case Intake/Case Analysis ที่มีบางส่วนต่อจริงแล้ว) รีเฟรชหน้าแล้วข้อมูลทั้งหมดหายกลับสู่ค่าเริ่มต้น 4 เคสตัวอย่าง "อนุมัติ/ไม่อนุมัติ" ในหน้านี้เป็นปุ่มจำลองการกดของผู้บริหาร (`btn-mock-approve`/`btn-mock-reject`) อยู่ในหน้าเดียวกับที่ทีมควบคุมโรคสร้างคำขอ ไม่ใช่ workflow แยกหน้า/แยกสิทธิ์แบบ รง.506 ในสาย B ของ `USER-JOURNEY-case-analysis.md`

## Persona

**หลัก — ทีมควบคุมโรค (ทีมพ่น)** เจ้าหน้าที่ที่รับเคสยืนยันแล้วจาก Case Intake/Case Analysis มาวางแผนพ่นสารเคมีกำจัดยุงลายตามมาตรฐาน Day 0/1/7 และร่างใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมีตามฟอร์มจริงของหน่วยงานก่อนส่งขออนุมัติ

**รอง — ผู้บริหาร/หัวหน้างาน** ผู้พิจารณาอนุมัติ/ไม่อนุมัติคำขอเบิกน้ำมัน/น้ำยาเคมีที่ทีมควบคุมโรคส่งมา — ในรุ่น prototype ปัจจุบันบทบาทนี้ไม่มีหน้า/สิทธิ์แยกจริง เป็นเพียงปุ่มจำลอง 2 ปุ่ม ("อนุมัติ (จำลองผู้บริหารกดอนุมัติ)" / "ไม่อนุมัติ (จำลองผู้บริหารกดไม่อนุมัติ)") ที่ปรากฏในหน้าเดียวกันหลังทีมควบคุมโรคกด "ส่งขออนุมัติ"

## Trigger

ทีมควบคุมโรคได้รับเคสที่ยืนยันแล้วจาก Case Intake (และ/หรือ cluster ที่ยืนยันแล้วจาก Case Analysis) ต้องวางแผนควบคุมโรค (พ่นสารเคมี) ในพื้นที่ที่เกี่ยวข้อง และต้องขออนุมัติเบิกน้ำมัน/น้ำยาเคมีสำหรับรอบปฏิบัติงานนั้น

## Pain point ที่ journey นี้แก้ (และที่ยังแก้ไม่ได้ในรุ่นนี้)

- ✅ แก้แล้ว: เดิมทีมควบคุมโรคต้องคำนวณวัน Day 0/1/7 และกรอกใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมีด้วยมือทุกช่องตามฟอร์มกระดาษ — ตอนนี้ระบบคำนวณวันที่ไทยจริงให้อัตโนมัติจากวันพบเคส และร่างเอกสารขออนุมัติที่ตรงฟอร์มจริงของหน่วยงานทุกช่องให้ทันที ลดเวลาป้อนข้อมูล/พิมพ์เอกสารซ้ำ
- ⚠️ ยังไม่แก้ (backlog):
  - ไม่มี workflow อนุมัติจริงที่ผู้บริหารเซ็นได้เองจากระบบ — ขั้นตอน 10a/10b เป็นปุ่มจำลองในหน้าเดียวกับทีมควบคุมโรค ไม่ใช่บทบาท/สิทธิ์/หน้าจอแยกจริง (`FEAT-CONTROL-03`, ROADMAP.md Phase 3)
  - ไม่มี real-time tracking ทีมพ่นภาคสนามจริง — ต้องพึ่งแอป LIFF แยกที่ยังไม่ได้พัฒนา ตารางในขั้นตอน 4-5 เป็นการวางแผนล่วงหน้าเท่านั้น ไม่ใช่ตำแหน่งจริงระหว่างปฏิบัติงาน (`FEAT-CONTROL-04`, Phase 3)
  - ไม่มี AI vision QC ตรวจรูปภาคสนามจริง (ต้องเก็บพิกัดตอนถ่ายผ่านแอปที่ยังไม่มี) — การรายงานภาพยืนยันพ่นแล้วอยู่นอกขอบเขต journey นี้ (`FEAT-CONTROL-05`, Phase 3, เกี่ยวข้องกับหน้า Field Tracking มากกว่า)
  - ข้อมูลทั้งหมดในหน้านี้ (จุดควบคุมโรค/สถานะพ่นแล้ว/คำขออนุมัติ) เป็น state ในหน่วยความจำของหน้าเว็บเท่านั้น รีเฟรชหน้าแล้วหายกลับสู่ 4 เคสตัวอย่างเริ่มต้นเสมอ — ไม่มี `CONTROL_LOCATION`/`SPRAY_ASSIGNMENT`/`APPROVAL_REQUEST` persist ลง Firestore จริงเลยในรุ่นนี้ (ต่างจาก รง.506 ในสาย B ของ `USER-JOURNEY-case-analysis.md` ที่ persist จริงแล้ว)
  - เคสในหน้านี้เป็น mock data ชุดใหม่ที่ตั้งชื่อพื้นที่ให้สอดคล้องกับ Case Analysis/Case Intake เพื่อความสมจริงเท่านั้น **ไม่ได้ดึงเคสที่ยืนยันแล้วจริงจากสองโมดูลนั้นมาต่อกันเป็น pipeline เดียว** — trigger ของ journey นี้ ("ได้รับเคสที่ยืนยันแล้วจาก Case Intake") จึงยังเป็นการเชื่อมโยงเชิงแนวคิดเท่านั้น ไม่มี Feature ID เฉพาะรองรับการเชื่อมข้ามโมดูลนี้

## Traceability กับ Test Spec

โมดูล Control Plan **ยังไม่มี Test Spec** ใน [[../../03-testing/01-test-plan/v1/ACCEPTANCE-CRITERIA|ACCEPTANCE-CRITERIA.md]]/`TEST-PLAN.md` เลย (เอกสารชุดปัจจุบันมีแค่ FR-DASH-01 ถึง 06 สำหรับ Outbreak Dashboard) — จึงไม่มีขั้นตอนใดใน journey นี้ที่ map กับ FR- ที่มีอยู่ได้ **ควรเรียก `qa-doc-builder` ต่อ** เพื่อเขียน Test Plan/Acceptance Criteria ของ `FEAT-CONTROL` โดยเฉพาะ

ขั้นตอน 1-9 และ 10a/10b/11 map ตรงกับ `DETAILED-DESIGN.md` Flow 8 (ขั้นตอน 8-11), Flow 9 (ขั้นตอน 4-5a) และ Flow 10 (ขั้นตอน 2-3) แบบ 1:1 อยู่แล้ว — ทั้ง 3 Flow เองก็ยังไม่มี Test Spec คู่กัน เมื่อเขียน Test Spec ควรใช้ Sequence Flow เหล่านี้เป็นฐานได้ทันที (Flow 8 มี state diagram ของ `APPROVAL_REQUEST` แนบให้แล้วด้วย เหมาะเป็นฐานเขียน test case ของสถานะ `draft/sent/approved/rejected` โดยตรง) — เป็นโมดูลที่ implement UI ครบแล้วในระดับ mock (ไม่ใช่ placeholder ว่างเปล่า) จึงพร้อมเขียน Test Spec ได้ทันทีแม้ยังไม่ต่อ backend จริง
