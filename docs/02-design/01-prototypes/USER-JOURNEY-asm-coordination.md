# User Journey — อสม. ส่งรูปยืนยันพ่นสารเคมีผ่าน LINE และทีมควบคุมโรคติดตามคิวแจ้งเตือนล่วงหน้า

อ้างอิงจาก [[../../01-requirements/01-spec/FEATURE-LIST|FEATURE-LIST.md]] หมวด `FEAT-ASM` และสอดคล้องกับ Sequence Flow ที่มีอยู่แล้วใน [[../02-technical/DETAILED-DESIGN|DETAILED-DESIGN.md]] Flow 13 (Photo Intake Query/Filter) และ Flow 14 (Advance Notice Queue) — โมดูลนี้**ยังไม่มี Test Spec** ใน [[../../03-testing/01-test-plan/v1/ACCEPTANCE-CRITERIA|ACCEPTANCE-CRITERIA.md]] เลย (มีแค่ FR-DASH-01 ถึง 06 สำหรับ Outbreak Dashboard) ดูหัวข้อ Traceability ท้ายเอกสาร

> **สถานะโค้ดจริง ณ วันที่เขียน (2026-09-22)**: โมดูลนี้**ทั้งหมดยังเป็น mock ล้วน** ฝังอยู่ใน `asm-coordination.js` (รูปภาพ 10 รูป และคิวแจ้งเตือน 5 แถว เป็น array คงที่ในหน่วยความจำของหน้าเว็บ ไม่มีส่วนไหนต่อ Firestore/LINE OA จริงเลย — เหมือน Control Plan/Field Tracking) รีเฟรชหน้าแล้วข้อมูลกลับสู่ชุดตัวอย่างเดิมเสมอ **และต่างจากโมดูลอื่นตรงที่ครึ่งแรกของ journey นี้ (การที่ อสม. ถ่ายรูป/ส่งรูปเข้า LINE OA จริง) ไม่มี UI จำลองใดๆ รองรับเลยแม้แต่ mock** — prototype เริ่มต้นที่มุมมองของ**ทีมควบคุมโรค**ที่เห็นผลลัพธ์รูปที่ "ถูกส่งเข้ามาแล้ว" เท่านั้น

## Persona

**หลัก — อสม. (อาสาสมัครสาธารณสุขประจำหมู่บ้าน)** ผู้ลงพื้นที่พ่นสารเคมี/กำจัดแหล่งเพาะพันธุ์ยุงลายตามแผนปฏิบัติงานที่ทีมควบคุมโรคมอบหมาย (ต่อเนื่องจาก Control Plan) แล้วต้องถ่ายรูปยืนยันการพ่นส่งกลับเข้าระบบเพื่อให้ทีมควบคุมโรคทราบสถานะ — **ในรุ่น prototype ปัจจุบัน บทบาทนี้ไม่มีหน้า/ช่องทางจริงให้ อสม. ใช้เลย** การ "ส่งรูป" ทั้งหมดเป็นเพียงข้อมูลตั้งต้น (10 รูปตัวอย่าง) ที่ฝังไว้ล่วงหน้าใน mock data โดยไม่มี flow การส่งจริงให้ดู

**รอง — ทีมควบคุมโรค** ผู้เปิดหน้า "ASM Coordination" เพื่อดูรูปที่ อสม. ส่งเข้ามา (จัดหมวดหมู่โดย AI vision ตามพื้นที่/วันที่ พร้อมสรุปสถานะพ่นแล้ว/ยังไม่พ่น) และตรวจสอบคิวแจ้งเตือนล่วงหน้าก่อนวันพ่นจริง (รอบ 1 ก่อน Day 0, รอบ 2 ก่อน Day 0+7) — persona นี้คือผู้ใช้งานจริงเพียงฝ่ายเดียวที่มี UI รองรับใน prototype รอบนี้

## Trigger

อสม. ได้รับมอบหมายให้ไปพ่นสารเคมี/กำจัดแหล่งเพาะพันธุ์ในพื้นที่ตามแผนปฏิบัติงาน (ต่อเนื่องจาก Control Plan) แล้วต้องส่งรูปยืนยันการพ่นกลับเข้าระบบ ขณะเดียวกันทีมควบคุมโรคต้องการดูคิวแจ้งเตือนล่วงหน้าก่อนวันพ่นจริง เพื่อให้แน่ใจว่าข้อความแจ้ง อสม./ประชาชนในพื้นที่ถูกส่งตรงเวลา

## Pain point ที่ journey นี้แก้ (และที่ยังแก้ไม่ได้ในรุ่นนี้)

- ✅ แก้แล้ว (เฉพาะฝั่งทีมควบคุมโรค, ระดับ mock): เดิมทีมควบคุมโรคต้องไล่ดูรูปที่ อสม. ส่งเข้า LINE ส่วนตัว/กลุ่มแชทเองทีละรูปโดยไม่มีการจัดหมวดหมู่ — prototype แสดงให้เห็นว่าเมื่อมีข้อมูลรูปพร้อมสถานะ AI vision แล้ว ทีมควบคุมโรคกรองตามพื้นที่/ช่วงวันที่ได้ทันทีและเห็นสรุปจำนวนพ่นแล้ว/ยังไม่พ่นโดยไม่ต้องนับเอง
- ✅ แก้แล้ว (เฉพาะฝั่งทีมควบคุมโรค, ระดับ mock): เดิมต้องพิมพ์ข้อความแจ้งเตือน อสม./ประชาชนเองทุกครั้งก่อนวันพ่น — prototype มีตัวอย่างข้อความ template ที่แทรกพื้นที่/วันที่ให้อัตโนมัติ ให้ตรวจสอบความถูกต้องก่อนได้
- ⚠️ ยังไม่แก้ (backlog):
  - ไม่มีช่องทางให้ อสม. ส่งรูปจริงเข้าระบบเลย — ไม่มีแม้แต่ mock UI ฝั่ง อสม. ขั้นตอน 1-2 ทั้งหมดเป็นแนวคิดที่ยังไม่มีอะไรให้คลิกดูจริง (`FEAT-ASM-03`, ROADMAP.md Phase 4)
  - ไม่มีการส่งข้อความแจ้งเตือนจริงผ่าน LINE Messaging API — badge "ส่งแล้ว"/"รอส่ง" เป็นค่าคงที่ ไม่เปลี่ยนตามเวลาจริง และไม่มีข้อความส่งออกจริง (`FEAT-ASM-04`, Phase 4)
  - สถานะพ่นแล้ว/ยังไม่พ่นเป็นผล AI แบบ read-only ทั้งหมด ไม่มี manual override ให้ทีมควบคุมโรคแก้ไขเมื่อ AI ตีความผิด (ยืนยันเป็น business rule ของ `FEAT-ASM-01` ใน `DETAILED-DESIGN.md` Flow 13 ไม่ใช่ backlog แต่เป็นข้อจำกัดโดยตั้งใจของรุ่นนี้)
  - ข้อมูลรูป/คิวแจ้งเตือนทั้งหมดเป็น state ในหน่วยความจำของหน้าเว็บเท่านั้น รีเฟรชแล้วหายกลับสู่ 10 รูป/5 แถวตัวอย่างเริ่มต้นเสมอ — ไม่มี `ASM_PHOTO_INTAKE`/`ADVANCE_NOTICE_QUEUE` persist ลง Firestore จริงเลยในรุ่นนี้ (เหมือน Control Plan/Field Tracking)
  - ชื่อพื้นที่ในหน้านี้ตั้งให้สอดคล้องกับ Control Plan/Field Tracking/Case Analysis เพื่อความสมจริงเท่านั้น **ไม่ได้ดึงพื้นที่ที่ทีมควบคุมโรควางแผนพ่นจริงจาก Control Plan มาต่อกันเป็น pipeline เดียว** — trigger ของ journey นี้ ("ได้รับมอบหมายให้ไปพ่นตามแผนปฏิบัติงาน") จึงยังเป็นการเชื่อมโยงเชิงแนวคิดกับ `USER-JOURNEY-control-plan.md` เท่านั้น ไม่มี Feature ID เฉพาะรองรับการเชื่อมข้ามโมดูลนี้

## Traceability กับ Test Spec

โมดูล ASM Coordination **ยังไม่มี Test Spec** ใน [[../../03-testing/01-test-plan/v1/ACCEPTANCE-CRITERIA|ACCEPTANCE-CRITERIA.md]]/`TEST-PLAN.md` เลย (เอกสารชุดปัจจุบันมีแค่ FR-DASH-01 ถึง 06 สำหรับ Outbreak Dashboard) — จึงไม่มีขั้นตอนใดใน journey นี้ที่ map กับ FR- ที่มีอยู่ได้ **ควรเรียก `qa-doc-builder` ต่อ** เพื่อเขียน Test Plan/Acceptance Criteria ของ `FEAT-ASM` โดยเฉพาะ

ขั้นตอน 3-6 map ตรงกับ `DETAILED-DESIGN.md` Flow 13 (Photo Intake Query/Filter) แบบ 1:1 และขั้นตอน 7-9 map ตรงกับ Flow 14 (Advance Notice Queue) เกือบ 1:1 **ยกเว้นจุดเดียว**: Flow 14 ระบุ conditional (`alt/else`) ให้ซ่อนตัวอย่างข้อความเมื่อ reminder สถานะ "ส่งแล้ว" แต่ `asm-coordination.js` จริงไม่ตรวจสถานะนี้เลย แสดงตัวอย่างทั้งคู่เสมอ — เมื่อเขียน Test Spec ควรใช้พฤติกรรม prototype จริงเป็นฐาน (ดูหมายเหตุในขั้นตอนที่ 8) และพิจารณาว่าจะแก้ Flow 14 ให้ตรงกับโค้ด หรือแก้โค้ดให้ตรงกับ Flow 14 เป็นการตัดสินใจแยกที่ยังไม่ได้ยืนยัน — ทั้ง 2 Flow เองก็ยังไม่มี Test Spec คู่กัน เมื่อเขียน Test Spec ควรใช้ Sequence Flow เหล่านี้เป็นฐานได้ทันที ขั้นตอน 1-2, 10-11 (ทั้งหมดเป็น backlog) ไม่มี Flow ใน `DETAILED-DESIGN.md` รองรับเลยเพราะยังไม่มี component จริงให้ออกแบบ sequence — เป็นโมดูลที่ implement UI ครบแล้วในระดับ mock สำหรับฝั่งทีมควบคุมโรค (ไม่ใช่ placeholder ว่างเปล่า) จึงพร้อมเขียน Test Spec ได้ทันทีแม้ยังไม่ต่อ backend จริง แต่ Test Spec ที่จะเขียนต้องครอบคลุมเฉพาะฝั่งที่มี UI จริง (ขั้นตอน 3-9) เท่านั้น เพราะฝั่ง อสม. (ขั้นตอน 1-2, 10-11) ไม่มีอะไรให้ทดสอบได้จริงในรุ่นนี้
